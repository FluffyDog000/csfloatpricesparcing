# CSFloat Sales Tracker

Собирает **полную** историю продаж по выбранным предметам CS2 с вкладки
**"Latest Sales"** на CSFloat и складывает её в локальную SQLite-базу, обходя
ограничение сайта (видно только последние ~40 продаж, старые исчезают).
Затем строит статистику: средняя/медианная цена по бакетам float, срезы по
paint seed, тренды.

> **Дисклеймер.** Вкладка "Latest Sales" обслуживается недокументированным
> внутренним эндпоинтом фронтенда CSFloat. Скрипт повторяет тот же запрос, что
> делает браузер, используя твою сессию (cookie/токен). Соблюдай разумный
> rate limit (в конфиге по умолчанию ~1 запрос/сек и опрос раз в 15–30 минут
> на предмет).

---

## Как это работает

1. `items.yaml` — список отслеживаемых предметов (`market_hash_name`).
2. `run_collector.py` — раз в 15–30 минут (рандомизированный джиттер) на каждый
   предмет опрашивает эндпоинт, парсит продажи и кладёт **только новые** в базу
   (`INSERT OR IGNORE` по уникальному `sale_id` → дублей нет).
3. Если между опросами окно из 40 продаж успело «прокрутиться» (совпадений с
   прошлым опросом почти нет) — в лог падает предупреждение «возможен пропуск».
4. `report.py` — строит отчёты по накопленным данным.

## Шаг 1. Получить cookie/токен через DevTools

Секреты берутся **только** из `.env`, в коде их нет.

1. Открой в браузере страницу нужного предмета на CSFloat и войди в аккаунт.
2. Нажми **F12** → вкладка **Network** → фильтр **Fetch/XHR**.
3. На странице предмета открой вкладку **"Latest Sales"** (если уже открыта —
   переключись на другую и обратно, чтобы запрос ушёл заново).
4. В списке запросов найди тот, что идёт на путь вида
   **`.../history/.../sales`** (или похожий — именно он отдаёт список продаж).
5. Правой кнопкой по запросу → **Copy → Copy as cURL (bash)**.
6. Из скопированного cURL достань значения заголовков:
   - **`Cookie: ...`** → всё, что после `Cookie: `, вставь в `CSFLOAT_COOKIE`.
   - если есть **`authorization: ...`** → вставь его значение в
     `CSFLOAT_AUTHORIZATION` (без слова `authorization:`).
   - обычно нужен либо cookie, либо токен; если есть оба — укажи оба.
7. Проверь в cURL сам **URL** запроса. Если путь отличается от
   `/api/v1/history/{name}/sales`, поправь `http.sales_path_template` в
   `config.yaml` (`{name}` подставляется автоматически, URL-энкодинг делает
   скрипт).

> Cookie/сессия со временем протухают. Если в логах появляются ошибки
> **AUTH ERROR (401/403)** — просто повтори шаги 1–6 и обнови `.env`. Скрипт при
> этом не падает: он логирует ошибку и пробует снова на следующем цикле.

### Свериться, что поля распарсились правильно

При первом успешном опросе каждого предмета скрипт сохраняет **сырой ответ** API
в `raw_dumps/<имя>.json`. Открой этот файл и убедись, что поля цены / float /
paint seed / времени продажи распознаются. Парсер (`src/parser.py`) намеренно
ищет поля по нескольким возможным путям (защитно), поэтому переносит небольшие
отличия структуры. Если что-то не совпало — поправь списки путей вверху
`src/parser.py` (там подробный комментарий) или пришли мне этот дамп, и я
подгоню маппинг.

## Шаг 2. Настроить список предметов

`items.yaml`:

```yaml
items:
  - name: "★ Specialist Gloves | Lt. Commander (Field-Tested)"
    pattern_sensitive: true    # влияет ли paint seed на цену (по умолч. true)
  - name: "AK-47 | Redline (Field-Tested)"
    pattern_sensitive: false   # seed не важен → таблица Paint seeds свёрнута
    interval_min_minutes: 10   # для быстро продающихся — чаще
    interval_max_minutes: 20
```

Имя должно совпадать с `market_hash_name` как на CSFloat (ключ можно писать как
`name`, так и `market_hash_name`). Удалённые из файла предметы помечаются в базе
неактивными (история не теряется).

**`pattern_sensitive`** (необязательное, по умолчанию `true`) — важен ли для
цены конкретный paint seed. Для скинов, где seed решает (Case Hardened, Doppler
и т.п.) — `true`. Для остальных — `false`: тогда на странице предмета таблица
**Paint seeds** свёрнута по умолчанию (открывается кликом по заголовку), чтобы не
отвлекать. На сбор данных флаг не влияет — paint seed сохраняется в БД всегда.

> ⚠️ **`items.yaml` — это только начальный импорт.** Он читается **один раз**,
> когда база пустая (первый запуск). Дальше список предметов живёт **в базе** и
> редактируется через веб-дашборд (см. «Управление предметами через веб» ниже);
> правки в `items.yaml` после первого старта ни на что не влияют.

## Шаг 3. Тест на 1–2 предметах перед постоянным сбором

Оставь в `items.yaml` один-два предмета и сделай один опрос:

```bash
python run_collector.py --once
```

Проверь:
- в консоли/логе строка `'<item>': fetched=N new=N overlap=0`;
- появился файл `raw_dumps/<item>.json` — глянь, что поля на месте;
- отчёт печатается:

```bash
python report.py --item "★ Specialist Gloves | Lt. Commander (Field-Tested)" --period all
```

Если всё ок — добавляй остальные предметы и запускай постоянный сбор.

## Шаг 4. Постоянный сбор

```bash
python run_collector.py
```

Крутится в цикле, опрашивая каждый предмет раз в 15–30 минут с джиттером,
размазывая запросы по времени. Останов — **Ctrl+C**.

### Фоновый запуск на Windows

**Вариант A — просто свернуть окно.** Запусти в отдельном окне PowerShell:

```powershell
python run_collector.py
```

**Вариант B — Task Scheduler (Планировщик заданий), автозапуск при входе.**

1. Создай `run_collector.bat` рядом с проектом:
   ```bat
   @echo off
   cd /d "%~dp0"
   call .venv\Scripts\activate.bat
   python run_collector.py
   ```
2. Открой **Task Scheduler** → **Create Task**.
3. **General**: имя `CSFloat Collector`; отметь *Run whether user is logged on
   or not* (по желанию) и *Run with highest privileges* — не обязательно.
4. **Triggers**: *At log on* (или по расписанию).
5. **Actions**: *Start a program* → путь к `run_collector.bat`.
6. **Settings**: сними *Stop the task if it runs longer than...* (сборщик
   долгоживущий).

**Вариант C — периодический `--once` по расписанию.** Вместо постоянного
процесса можно попросить Task Scheduler запускать `python run_collector.py --once`
каждые, например, 20 минут (триггер *Repeat task every 20 minutes*). Тогда
джиттер не нужен, но следи, чтобы интервал был достаточно частым и окно 40
продаж не прокручивалось (см. предупреждения в логе).

Логи пишутся в `logs/collector.log` с ротацией (5 файлов по 5 МБ).

## Отчёты

```bash
# Список отслеживаемых предметов
python report.py --list

# Сводка по бакетам float и по paint seed за 7 дней (таблицы в консоли)
python report.py --item "★ Specialist Gloves | Lt. Commander (Field-Tested)"

# Другой период и размер бакета
python report.py --item "AK-47 | Redline (Field-Tested)" --period 30d --bucket 0.02

# Только конкретный paint seed (напр. посмотреть среднюю цену для seed=13)
python report.py --item "..." --seed 13

# Выгрузить точные строки продаж в CSV
python report.py --item "..." --period 30d --csv sales.csv
```

Периоды: `24h`, `7d`, `2w`, `all`. Отчёт показывает:
- **Overall** — общее число продаж и avg/median/min/max цены за период;
- **Float buckets** — разбивка по диапазонам float (размер бакета из
  `config.yaml` или `--bucket`) с count/avg/median/min/max — видно, что за более
  редкий/низкий float переплачивают;
- **Paint seeds** — срез по paint seed.

## Веб-дашборд (часть 2)

Веб-интерфейс поверх той же БД: карточки предметов, страница предмета с
раскрывающимися таблицами float-бакетов и paint seed, живое автообновление.

### Запуск дашборда

```bash
python webapp.py
```
Открой **http://localhost:5000**. Порт/адрес меняются в `config.yaml` (секция
`web`) или через `CSFLOAT_WEB_PORT` / `CSFLOAT_WEB_HOST`.

- **Главная** — карточки предметов (картинка, название, всего продаж, avg/min/max)
  + **поиск**: поле сверху фильтрует карточки по названию на лету (без перезагрузки).
- **Страница предмета** — переключатель периода (7д / 30д / всё время); таблицы
  **Float buckets** и **Paint seeds**; клик по строке разворачивает список
  конкретных продаж (float, seed, цена, дата, стикеры), подтягивается отдельным
  AJAX-запросом. Данные сами обновляются каждые ~45с без перезагрузки; уже
  раскрытые строки при этом не схлопываются. В шапке — «данные актуальны на
  HH:MM» (краснеет, если сбор завис >1ч).

### Период и колонка count

- **Переключатель периода**: 7 дней / 30 дней / всё время, плюс **«Период…»** —
  произвольный диапазон дат «с … по …».
- Колонка **count** в обеих таблицах — число продаж за выбранный период.
  **Клик по заголовку** сортирует (убыв. → возр. → выкл.). Подсветка
  относительно самого предмета: медиана count среди бакетов/seed → 🟢 много
  (≥ 1.5× медианы) / 🟡 / 🔴 мало (< 0.5×). Если групп < 4 — без цвета.
  Коэффициенты — в константах вверху `static/item.js` (`COUNT_FAST_MULT` и т.д.).

### Управление предметами через веб

Кнопка **«Управление»** на главной открывает панель. **Источник истины —
база данных**: `items.yaml` импортируется только один раз при первом старте на
пустой БД, дальше всё редактируется через веб, а сборщик подхватывает изменения
**без перезапуска** (в течение ~30с).

- **Добавить предмет** — ввести `market_hash_name`, папку (необязательно), флаг
  «паттерн важен».
- **Пауза / Возобновить** — остановить сбор по предмету, **сохранив историю**.
- **🎨 паттерн** — переключить `pattern_sensitive` (влияет на сворачивание
  таблицы Paint seeds).
- **📁 папка** — отправить предмет в папку (на главной карточки группируются по
  папкам, есть фильтр по папке).
- **🗑 удалить** — убрать предмет **вместе с историей продаж** (с
  подтверждением). Нужно сохранить историю, но перестать собирать → используй
  **Паузу**, а не удаление.

> **Безопасность (для сервера).** Эндпоинты изменения по умолчанию открыты
> (удобно локально). Если выставляешь дашборд наружу — задай `CSFLOAT_ADMIN_TOKEN`
> в `.env`: тогда изменения требуют токен (поле появится в панели «Управление»,
> токен хранится в браузере). Читающие эндпоинты токеном не защищены —
> для публичного доступа ставь дашборд за reverse-proxy с авторизацией.

### Вкладка «📊 Нагрузка» и лимиты CSFloat

Показывает здоровье сбора: сколько активных предметов, оценка запросов/мин,
опросы за час/сутки (ok / 429 / auth / ошибки), предупреждения о пропусках и
лента последних опросов.

**Если появились 429** («429 за час» горит красным) — CSFloat режет по лимиту.
Что делает бот сам:
- при 429 включается **глобальная пауза** для всех предметов (1 → 2 → 4 … мин,
  максимум 15) вместо долбёжки по одному предмету; в логе `Rate-limited by
  CSFloat; polling paused for N min`. Успешный ответ сбрасывает эскалацию;
- на старте первый круг опроса **размазан** по интервалу, а не идёт пачкой.

**Главное ограничение — квота, а не скорость.** CSFloat присылает в каждом
ответе заголовки `x-ratelimit-limit` / `x-ratelimit-remaining` /
`x-ratelimit-reset`: это **общее число запросов на окно** (у нас наблюдалось
500). Сколько бы ни была пауза между запросами, после исчерпания квоты всё
упирается в 429 до сброса. Поэтому бот:
- читает остаток квоты из каждого ответа и показывает его плиткой
  «квота CSFloat» (осталось / всего / когда сброс);
- **растягивает все интервалы** так, чтобы запланированные запросы уложились в
  оставшуюся квоту до сброса (коэффициент виден в подсказке под настройками);
- при остатке около нуля **полностью останавливает опрос** до сброса, а не
  бьётся в 429.

Практический вывод: при квоте 500/сутки и 164 предметах на каждый предмет
приходится ~3 опроса в день (раз в ~8 часов). Хочешь чаще — уменьшай число
отслеживаемых предметов.

### Прокси: несколько квот вместо одной

Квота считается **по IP** (проверено: домашний браузер и сервер имеют независимые
счётчики), поэтому каждый прокси добавляет свои ~500 запросов в сутки.

Прокси задаются **на вкладке «Нагрузка» → «Прокси»**: по одному адресу в строке,
можно вставить сразу весь список. Поддерживаются `http://`, `https://`,
`socks5://` (`socks5h://`, `socks4://`); логин и пароль пишутся прямо в строке:

```
http://user:pass@host:8080
socks5://host:1080
```

Чекбокс «использовать и собственный IP сервера» отвечает за прямое соединение
(его квота суммируется с прокси). Список лежит в базе — сборщик перечитывает его
**каждые ~30 секунд**, перезапускать ничего не нужно; квота уже известных
маршрутов при этом сохраняется. Некорректные строки не сохраняются: форма
покажет, что именно не так.

В `.env` те же значения можно задать для первого запуска — при пустой базе они
один раз копируются в неё, дальше источник правды — база и дашборд:

```
CSFLOAT_PROXIES=http://user:pass@host:8080, socks5://host:1080
CSFLOAT_USE_DIRECT=1      # 0 — ходить только через прокси, минуя IP сервера
```

Как это работает: у каждого маршрута (включая прямое соединение) своя квота;
перед каждым запросом бот берёт тот, где остаток больше. Маршрут, поймавший 429,
уходит в паузу **один** — остальные продолжают работать; маршрут с сетевыми
ошибками временно выводится из ротации. Суммарная квота видна на вкладке
«Нагрузка», там же таблица **«Маршруты (прокси)»** с остатком по каждому.
Пароли из строк подключения нигде не логируются и не показываются.

> ⚠️ Учти риск: CSFloat отдельно отслеживает, с скольких IP ходит один аккаунт
> (сообщение «too many requests from too many IPs»). Много прокси на одну
> сессию — заметный паттерн; аккаунт могут ограничить сильнее, чем один IP.

#### Ротационные прокси

Ротационный прокси (новый выходной IP на каждый запрос) поддерживается, но
требует отдельной пометки — суффикс `#rotating` в строке:

```
http://user:pass@gate.provider.com:7000 #rotating
```

Почему нельзя просто вставить его как обычный прокси: заголовки `x-ratelimit-*`
приходят от того IP, который обслужил конкретный запрос, то есть от чужого
бюджета. Без пометки бот увидит «остаток всегда ~500» и перестанет ограничивать
темп вообще. Помеченный маршрут считается **локальным счётчиком**: поле
«лимит ротационного» в блоке «Прокси» задаёт, сколько запросов в сутки через
него разрешено (по умолчанию 500 — столько же, сколько даёт один IP).
Счётчик переживает перезапуск, так что рестарт не выдаёт новую сотню запросов.

Два правила, которые бот соблюдает сам:

- **Ротация — только на переполнение.** Пока у фиксированных маршрутов
  (свой IP и обычные прокси) есть квота, ротационный не используется вообще.
  Каждый запрос через ротацию показывает CSFloat ещё один IP того же аккаунта —
  ровно то, что считает его проверка «too many IPs».
- **Реакция на жалобу аккаунта.** Если в ответе приходит
  `too many requests from too many IPs`, бот отличает это от обычного 429:
  ротационные маршруты паркуются на 6 часов, фиксированные продолжают работать,
  а на вкладке «Нагрузка» появляется предупреждение с датой.

Практический совет: у нормального провайдера есть **sticky-сессии** — тот же
шлюз, но IP держится 10–30 минут (обычно через логин вида
`user-session-ab12` или отдельный порт). Такой вариант лучше чистой ротации:
IP всё ещё несколько, но их единицы, а не сотни. Если провайдер это умеет —
бери sticky и НЕ ставь `#rotating`, тогда маршрут будет учитываться по обычным
заголовкам квоты.

#### Проверка прокси перед тем, как ставить его в работу

TTL, который ты пишешь в логине sticky-сессии (`…-ttl-30`), — это **просьба к
провайдеру**, а не гарантия: тариф может обрезать её до своего максимума либо
проигнорировать и выдавать новый IP на каждый запрос. Проверить, что получилось
на самом деле:

```bash
python check_proxy.py "edge1-us.example.me:8888:acct-sid-1-ttl-30:pw"
```

Скрипт показывает выходной IP, делает настоящий запрос к CSFloat твоей кукой и
выносит вердикт: годится / Cloudflare challenge / IP забанен / 429 сразу.
Логины и пароли в вывод не попадают.

Чтобы измерить, сколько на самом деле живёт IP:

```bash
python check_proxy.py "edge1-us.example.me:8888:acct-sid-1-ttl-30:pw" --watch 60
```

Час опроса покажет, сменился ли IP и через сколько минут. Держится дольше
окна — можно убирать `#rotating`; меняется чаще раза в час — оставляй.
`--direct` проверяет сам сервер без прокси.

Форматы строк, которые понимает поле ввода:

```
http://user:pass@host:8080          схема + логин
socks5://host:1080                  socks
host:8080:user:pass                 формат, в котором прокси продают
user:pass@host:8080                 без схемы (подставится http)
```

**Автоматика, которая держит темп (можно не трогать):**
- **Адаптивный интервал.** Каждый предмет опрашивается по своей скорости
  продаж: чтобы между опросами набегало ~10 продаж (при окне в 40 это
  четырёхкратный запас). Медленный скин, продающийся пару раз в день, не
  дёргается каждые 15 минут, а ходовой — опрашивается часто. На практике это
  снижает нагрузку в ~5 раз. Настраивается на вкладке «Нагрузка»: галочка
  «адаптивный интервал» и «потолок» (по умолчанию 120 мин); нижняя граница —
  твой «интервал от». Ручной интервал у конкретного предмета всегда главнее.
- **Авто-замедление (AIMD).** Поймали 429 → весь график растягивается ×1.5
  (до ×8). Час без единого 429 → ×0.9 обратно. Бот сам находит скорость,
  которую CSFloat терпит; текущий множитель виден в подсказке под настройками,
  сбросить можно кнопкой «Сбросить замедление».
- **Кулдаун переживает перезапуск** — иначе рестарт во время паузы сразу же
  ловил новый 429.
- **Диагностика**: в блоке «Диагностика лимита» видно время последнего 429 и
  заголовки, которые прислал CSFloat (`Retry-After`, `X-RateLimit-*`).

Что можно сделать руками, если 429 повторяются:
1. Увеличить интервалы опроса в `config.yaml` (главный рычаг — прямо снижает
   нагрузку):
   ```yaml
   polling:
     interval_min_minutes: 25
     interval_max_minutes: 45
   ```
2. Увеличить паузу между запросами там же: `min_seconds_between_requests: 4`.
3. Убрать часть предметов или поставить редко продающиеся на паузу.

Ориентир: `запросов/мин ≈ кол-во предметов / средний интервал в минутах`.
Например 164 предмета при 15–30 мин ≈ 7 запр/мин; при 25–45 мин ≈ 4.7.

### Картинки предметов

Берутся через официальный листинг-эндпоинт `GET /api/v1/listings` и требуют
`CSFLOAT_API_KEY` в `.env` (ключ из настроек аккаунта CSFloat). URL картинки
кэшируется в таблице `items` (перезапрос не чаще, чем раз в `images.refresh_days`
дней). **Без ключа дашборд работает** — вместо картинки показывается плейсхолдер.

### Одновременный запуск сборщика и дашборда (Windows)

Это два независимых процесса, работающих с одной SQLite-базой (включён режим
**WAL**, поэтому чтение дашбордом и запись сборщиком не конфликтуют — ошибок
`database is locked` не будет).

**Вариант A — два окна.** В одном:
```
python run_collector.py
```
Во втором:
```
python webapp.py
```

**Вариант B — один `.bat`, оба процесса.** Создай `start_all.bat`:
```bat
@echo off
cd /d "%~dp0"
call .venv\Scripts\activate.bat
start "CSFloat Collector" python run_collector.py
start "CSFloat Dashboard" python webapp.py
start "" http://localhost:5000
```
Двойной клик — поднимутся оба процесса в отдельных окнах и откроется браузер.

**Вариант C — Task Scheduler.** Заведи два задания (или одно на `start_all.bat`)
с триггером *At log on*, как описано выше в разделе про фоновый запуск сборщика.

### JSON API (если захочешь дёргать данные сам)

| Эндпоинт | Назначение |
|---|---|
| `GET /api/items` | список предметов со сводкой + `last_update` |
| `GET /api/item/aggregates?item=…&period=7d&bucket=0.01` | overall + бакеты + seeds |
| `GET /api/item/bucket_sales?item=…&bucket_lo=0.15&bucket_size=0.01&period=7d` | продажи внутри бакета |

`period`: `7d`, `30d`, `all`.

## Бэкап, восстановление и защита (часть 5)

Для размещения на сервере: ежедневный бэкап БД в Telegram, восстановление и
защита дашборда логином/паролем.

### Защита дашборда логином (обязательно перед выкладыванием в интернет)

1. Сгенерируй хэш пароля (пароль в открытом виде нигде не хранится):
   ```
   python set_password.py
   ```
   Скопируй строку `DASHBOARD_PASSWORD_HASH=…` в `.env`.
2. Задай `FLASK_SECRET_KEY` (подписывает сессию):
   ```
   python -c "import secrets; print(secrets.token_hex(32))"
   ```
3. По желанию поменяй `DASHBOARD_USERNAME` (по умолчанию `admin`) и
   `DASHBOARD_SESSION_DAYS` (жизнь сессии, дефолт 7 дней).

Когда `DASHBOARD_PASSWORD_HASH` задан, **весь** дашборд и все API требуют вход.
Без него дашборд открыт (удобно локально, но не для интернета). Защита от
подбора: после 7 неверных попыток вход блокируется на 5 минут.

> 🔒 **HTTPS обязателен, если открываешь наружу без VPN.** Без TLS пароль
> уходит по сети **в открытом виде** и его можно перехватить. Проще всего —
> поставить перед дашбордом **Caddy** (сам получает и продлевает сертификат
> Let's Encrypt). Минимальный `Caddyfile`:
> ```
> dashboard.example.com {
>     reverse_proxy 127.0.0.1:5000
> }
> ```
> `caddy run` — и всё работает по HTTPS. Дашборд при этом слушает только
> localhost (`CSFLOAT_WEB_HOST=127.0.0.1`), наружу смотрит только Caddy.
> Альтернатива — nginx + certbot. Настройку реверс-прокси делаешь один раз сам;
> без неё наружу дашборд лучше не выставлять.

### Ежедневный бэкап в Telegram

Токен бота и `chat_id` — в `.env` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).
На странице **⚙ Настройки**:
- галочка «включить» + **время по МСК** (например `03:30`) → сохранить;
- каждый день в это время сборщик снимает консистентный снапшот **всего файла
  БД** и отправляет его боту как документ (`sendDocument`). Время всегда
  считается по `Europe/Moscow`, независимо от таймзоны сервера. При ошибке
  отправки — повтор через 10 минут (не молча).
- кнопка **«Экспортировать сейчас»** — тот же экспорт вручную.

Планировщик встроен в процесс **сборщика** (`run_collector.py`) — отдельный
демон не нужен. Снапшоты/копии складываются в `data/backups/` (хранятся
последние ~20).

### Уведомления о проблемах в Telegram

На странице **⚙ Настройки** → «Уведомления о проблемах». Бот пишет в тот же
чат, если сбор встал:
- **протухла cookie** (401/403 и ни одного успешного опроса за час);
- **нет успешного сбора** дольше порога (по умолчанию 90 мин);
- **лимит 429 не отпускает** (за час только отказы).

Не чаще одного сообщения в час на каждую проблему; когда всё восстановилось,
счётчик сбрасывается сам.

### Восстановление БД

**Через веб** (⚙ Настройки → «Восстановление»): загрузи файл `*.db`. Сервер
проверит, что это валидная база трекера, **сохранит текущую БД в резервную
копию**, затем заменит файл. Сборщик подхватит замену автоматически.

**Через Telegram**: пришли боту файл `sales.db` как документ. Бот принимает его
**только с сохранённого `chat_id`** (сообщения от других чатов игнорируются),
делает копию текущей базы, заменяет и отвечает «База восстановлена из …». Если
файл битый/не та база — восстановление отклоняется, текущая база не трогается.

### Схема базы (SQLite)

- **items** — `id, market_hash_name (unique), added_at, active, last_polled_at`.
- **sales** — `sale_id (PK), item_id, market_hash_name, price_cents, price,
  float_value, paint_seed, paint_index, sold_at, sold_at_estimated,
  stickers_json, raw_json, scraped_at`.
  - `sale_id` = ID из API, а если его нет — детерминированный SHA1-хэш из
    `item|price|float|seed|sold_at`, чтобы дедуп работал при повторном опросе.
  - `sold_at_estimated=1`, если время получено из относительного («54 minutes
    ago») и вычислено на момент сбора.
- **poll_log** — журнал каждого опроса: сколько получено/новых/совпало, статус
  (`ok/auth_error/rate_limited/error`), заметки (в т.ч. предупреждение о
  пропуске).
